Before you test anything — the discovery pass

Days one to ten are not for writing test cases. They are for finding out which of the assumptions in this manual are actually true here, and for building the things that do not exist yet.

End the pass with what you now know to be untrue, unavailable or unowned — and say it out loud before writing a single case. A test plan built on unchecked assumptions tests the assumptions, not the product.

Conventions

Shashi Kumar is the QA engineer in every worked example. Stories LT-nnnn, incidents LT-INC-nnnn. Customer domains are school.edu — Lingotran sells to institutions, and that shapes almost every risk here.

The one fact to carry

~30 learners per class share one NAT IP on shared devices, many on iPad Safari, and many are minors. Every defect is multiplied by class size before anyone notices. If you remember nothing else, weight by that.

01 The QA operating model6 p

A set of gates, each with an owner and an exit condition. If you cannot name the gate a piece of work sits at, you cannot say whether it is ready.

1.1 What QA owns, and what it does not

ActivityOwnerQA's actual job
Unit testsDeveloperRead them in the PR. Judge whether they assert behaviour or implementation. Do not write them.
Acceptance criteriaQA + POWritten as Given/When/Then before the sprint opens. QA drafts, PO confirms.
Integration testsDeveloper + QAQA specifies the cases; either party implements.
End-to-end suiteQAOwned outright — authorship, stability, runtime, and the decision to delete flaky specs.
Exploratory chartersQATime-boxed, documented, and the single highest-yield activity in this table.
Performance baselinesQA + backendQA owns the scenario; a backend engineer owns the infrastructure it runs against.
Release go/no-goQAQA states risk in plain language. The business decides. QA never says "it's fine".
Production monitoringBackendQA defines what "wrong" looks like so alerts can be written against it. Nobody owns this full time — see 1.6.

Coverage gates are gamed

A global "80% coverage" target is met by testing getters. Gate on coverage of changed lines in the diff instead. It is the only coverage number that resists gaming, because it moves only when the author writes tests for the code they just wrote.

The institution multiplier

Lingotran sells to schools, not individuals. Every defect is multiplied by class size before anyone notices it. A bug affecting one learner is a ticket; the same bug on a shared classroom network is thirty simultaneous tickets and an escalation to the head of department. Weight likelihood accordingly.

1.4 Who QA depends on

QA is one engineer against roughly a dozen who write code. That ratio is the single biggest constraint in this manual, and it means most of QA's job is knowing who to go to rather than doing it all.

RoleWhat QA needs from themWhat happens when it is missing
Product managerConfirms acceptance criteria before the sprint opens; owns the go/no-go that QA informsQA invents the ACs, then tests its own guess

DB engineersMigration review, EXPLAIN at UAT volume, the standing checks in 6.2The 200-row lie ships (2.3)
UI/UXKeyboard order and non-colour feedback decided at design timeAccessibility becomes a defect log instead of a design property (9.3, 7.7)
Language SMEWhether the reference text itself is correctNobody can tell. QA cannot judge this and must not pretend to

Sales / marketingWhat was actually promised to a schoolSeverity gets set without knowing the contractual stake
FounderA same-day route for safeguarding and contract-level riskA safeguarding issue waits in a backlog (9.2)
There is no SRE, and no dedicated ops

Infrastructure, alerting and production monitoring have no full-time owner. QA still defines what "wrong" looks like, but somebody must be named to build the alert or it does not exist. Name a person in the RCA action, never a role. "Backend will add an alert" is how a corrective action quietly never happens (10.2).

One QA cannot run this table by hand

Count the rows marked QA. One engineer covers that surface only by refusing to do it manually — the pipeline runs regression, contract, isolation and load without asking. What stays manual is what automation cannot do: exploratory, real devices, and the judgement at sign-off. Manual effort anywhere else means something automatable was left undone.

Where the boundary sits

QA does not write unit tests, does not judge whether German or Kannada reference text is linguistically correct, and does not own infrastructure. QA does own whether the absence of those things is stated as a risk at sign-off. Unowned is not the same as untested — say which one it is.

1.7 Two products in one — B2B and B2C

Lingotran sells to institutions and direct to individuals. Almost everything in this manual was written B2B-first, because that is where the sharpest failures are. Read every risk through whichever column applies.

DimensionB2B · schoolsB2C · individualsWhat changes for QA

The institution multiplier does not apply to B2C

Weighting likelihood by class size is correct for schools and wrong for consumers. A B2C defect affects users one at a time — which makes it look lower severity right up until it is thousands of them, spread thin enough that nobody escalates. Score the two segments separately in 1.3, and never let a B2C issue inherit a B2B severity, or the reverse.
