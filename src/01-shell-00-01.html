01 The QA operating model3 p

QA at Lingotran is not a phase at the end of a sprint. It is a set of gates, each with an owner and an exit condition. If you cannot name the gate a piece of work is sitting at, you cannot say whether it is ready.

1.1 What QA owns, and what it does not

ActivityOwnerQA's actual job
Unit testsDeveloperRead them in the PR. Judge whether they assert behaviour or implementation. Do not write them.
Acceptance criteriaQA + POWritten as Given/When/Then before the sprint opens. QA drafts, PO confirms.
Integration testsDeveloper + QAQA specifies the cases; either party implements.
End-to-end suiteQAOwned outright — authorship, stability, runtime, and the decision to delete flaky specs.
Exploratory chartersQATime-boxed, documented, and the single highest-yield activity in this table.
Performance baselinesQA + SREQA owns the scenario; SRE owns the infrastructure it runs against.
Release go/no-goQAQA states risk in plain language. The business decides. QA never says "it's fine".
Production monitoringSREQA defines what "wrong" looks like so alerts can be written against it.

1.2 Quality gates

GateExit conditionBlocks what
ReadyACs testable, edge cases named, test data identifiedStory entering the sprint
PRBuild green, coverage on changed lines ≥ 80%, QA comment resolvedMerge to main
IntegrationAPI suite green against a real PostgreSQL containerDeploy to staging
StagingE2E green, exploratory charter complete, a11y scan cleanRelease candidate
ReleaseReadiness report signed, rollback rehearsedProduction deploy
Post-deploySmoke green on production, error rate flat for 30 minClosing the release
Coverage gates are gamed

A global "80% coverage" target is met by testing getters. Gate on coverage of changed lines in the diff instead. It is the only coverage number that resists gaming, because it moves only when the author writes tests for the code they just wrote.

1.3 Risk-based prioritisation

Everything cannot be tested. Score each area, test in descending order, and be able to defend the order out loud.

Lingotran areaImpactLikelihoodScoreWhy
Login & session5420Total lockout for a whole school; changes often
Speech capture & scoring5420The product's reason to exist; browser and device variance is huge
Lesson progress persistence5315Lost progress destroys trust and is unrecoverable
Teacher class reports4312Drives renewal conversations with institutions
Role-based access5210A student seeing another class's data is a safeguarding incident
Billing & seat counts428Contractual exposure, but changes rarely
Marketing pages133Embarrassing, not damaging
The institution multiplier

Lingotran sells to schools, not individuals. Every defect is multiplied by class size before anyone notices it. A bug affecting one learner is a ticket; the same bug on a shared classroom network is thirty simultaneous tickets and an escalation to the head of department. Weight likelihood accordingly.
