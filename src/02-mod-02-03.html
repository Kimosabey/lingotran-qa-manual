2.2 The layer trace — what QA validates at each hop

Every Lingotran request passes through these layers. When a PR changes one, test that row and every row below it.

1
React componentLessonPlayer.tsx
Loading, empty, error and success states all render. Disabled controls during submit. No secrets in props. Keyboard reachable.
2
API clientlib/apiClient.ts
Correlation ID attached. Timeout set. 401 triggers refresh exactly once, not a loop. Network failure surfaces a retry, not a blank screen.
3
Routeroutes/*.routes.ts
HTTP verb and path correct. Auth middleware present — and present on every sibling route, which is where it is usually missing.
4
Middlewareauthenticate, rateLimit
Order matters: validate before authenticate leaks schema; authenticate before rateLimit lets unauthenticated floods through. Check the order, not just the presence.
5
Validatorzod schema
Unknown keys stripped. Type coercion explicit. Error shape identical across endpoints. Rejects before any DB call.
6
Controller*.controller.ts
Maps result to status code. No business logic. No SQL. Never leaks an internal error message to the client.
7
Service*.service.ts
Where the rules live, so where most bugs live. Ownership checks, quota checks, state transitions. Test this layer hardest.
8
Repository*.repository.ts
Parameterised queries only. Transaction boundary wraps multi-write operations. Soft-delete filter applied.
9
PostgreSQLschema + indexes
Constraint enforces what code assumes. Index supports the query's WHERE. Migration is reversible.
10
ResponseJSON envelope
Shape matches the contract. Status code semantically right. No internal IDs, stack traces, or row counts.
11
React renderstate update
Optimistic update rolls back on failure. Stale response from a superseded request is discarded, not rendered.
Use it as a diff checklist

Open the PR, mark which layers the diff touches, and test that layer plus everything downstream. A change at layer 7 cannot break layer 1, but a change at layer 9 can break all ten above it.

2.3 Environments

Three environments, plus a throwaway database container inside the pipeline. Knowing what each one cannot prove matters more than knowing what it runs.

EnvDataSpeechWhat it can and cannot prove
Dev (http)Seed script, ~200 rowsOnly on localhost — a secure context by exceptionLogic only. Proves nothing about scale, real devices, or a class of thirty.
CI containerFresh PostgreSQL per runStubbedRegression and contract, deterministic by design. Not an environment anyone can open.
UAT (http)Anonymised copyBlocked — no secure contextThe only place before production where index and query-plan problems can appear — if it holds production-like volume.
ProductionLiveRealRead-only smoke against a dedicated canary account. Never exploratory testing.
Dev and UAT are HTTP — so the core feature cannot run there

Browsers only expose microphone and speech APIs in a secure context. Over plain http:// — with the single exception of localhost — the browser refuses:

APIOn HTTP UATConsequence
getUserMediaBlockedNo microphone. Nothing in Module 07 can be exercised on UAT
SpeechRecognitionBlockedNo transcript, so no score. The REF corpus cannot run here
Service workerBlockedoffline_lesson_cache is untestable outside production
Secure cookiesNot set or sentSession behaviour differs from production — LT-1187 proves nothing here
JWT in transitPlaintextTokens and learner data readable on the school network

A UAT sign-off on anything speech-related is currently worth nothing — the feature cannot execute. Fix it with TLS on UAT (a self-signed certificate suffices; the browser only checks for a secure context), or record it as accepted risk at every release (12.1).

UAT is doing the work of two environments

UAT is both where people click around and where load tests run, and those uses fight — a k6 burst during acceptance testing invalidates both. Book it, and run load nightly. Results only mean anything if UAT matches production on data volume and instance count; a single-instance UAT cannot reproduce the rate-limiter defect at all (2.4).

The 200-row lie

PostgreSQL will happily seq-scan 200 rows faster than it uses an index, so a missing index is invisible locally and in CI. It appears as gradually rising latency in production, then a timeout cliff. Any query added in a PR must be checked with EXPLAIN against UAT volumes, not local.

2.4 Configuration and multi-instance behaviour

Lingotran's API runs on two or more App Service instances. Anything holding state in process memory behaves differently in production than on your laptop.

In-process stateProduction consequenceTest approach
Rate limiter countersEffective limit = configured × instance countRun UAT at 2 instances and count actual rejections
In-memory cacheStale reads depending on which instance served youRepeat the same read 10× and compare
Scheduled job timersJob fires once per instance — duplicate emailsAssert exactly-one side effect, not "at least one"
WebSocket session mapReconnect lands on the other instance and loses contextForce a reconnect mid-lesson

2.5 Feature flags

FlagDefaultQA obligation
transcript_scoring_v2OffTest both states. Off is what most schools run; on is what the demo shows.

Rule

A flag doubles the state space of everything it touches. Test the transition, not just the two states — flags are flipped on live systems with users mid-lesson.

03 Requirements to test design4 p

3.1 Interrogating a story

Story LT-1187 · Sprint 42

As a teacher using Lingotran on my classroom laptop, I want a "Keep me signed in" option, so I don't re-authenticate between lessons.

AC1 Checkbox appears, unchecked by default. AC2 Checked → session persists 30 days; unchecked → 12 hours. AC3 The choice is not remembered between visits.

A junior engineer writes three test cases, one per criterion. Shashi Kumar writes none yet, and asks seven questions first:

Question the ACs do not answerWhy it changes the test plan
30 days from login, or 30 days of sliding inactivity?Different implementations and different security postures
What happens to an existing 12-hour session if the user logs in again with the box checked?Session upgrade is undefined; both behaviours are defensible
Does a password change invalidate 30-day sessions?If not, a compromised account stays compromised after the "fix"
Is this offered to student accounts on shared classroom devices?A 30-day session on a shared laptop is a safeguarding issue, not a UX preference
Can an admin see and revoke long-lived sessions?Without revocation the feature has no off switch during an incident
What does /refresh do with a 30-day token?Refresh chaining can extend a session indefinitely, defeating both limits
Is 30 days compatible with signed district contracts?Some education contracts cap session lifetime explicitly
The economics

Every question above came from reading three lines against an architecture diagram and a customer profile — before any code existed. Answering them costs one refinement conversation. Finding them in production costs an incident, a rollback, and possibly a contract.

Length is not character count

An 80-character limit enforced with str.length in JavaScript counts UTF-16 code units. a single emoji counts as 2, and a Devanagari cluster can be 4 or more. A learner named in Hindi or Tamil hits an 80-character limit at 20 visible characters. Always test the limit with non-Latin script — this is Lingotran's core user base.
