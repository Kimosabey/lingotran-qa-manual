export function RecordControl({ exerciseId, maxAttempts = 3 }: Props) {
  const [state, setState] = useState<'idle'|'recording'|'uploading'|'scored'|'error'>('idle');
  const [attempts, setAttempts] = useState(0);              // ① client-side counter
  const recorder = useRef<MediaRecorder|null>(null);

  async function start() {
    const stream = await navigator.mediaDevices.getUserMedia({ audio: true }); // ② can reject
    recorder.current = new MediaRecorder(stream, { mimeType: 'audio/webm' });   // ③ Safari
    setState('recording');
  }

  async function stop() {
    setState('uploading');
    const blob = await collect(recorder.current!);
    try {
      const r = await api.post(`/exercises/${exerciseId}/attempts`, blob);
      setAttempts(a => a + 1);                                 // ④ only on success
      setState('scored');
    } catch { setState('error'); }                           // ⑤ no retry offered
  }
  ...
}
#What QA reads hereTest that falls out of it
①Attempt count lives in component stateReload the page mid-exercise — does the limit reset? Server must be the authority.
②getUserMedia can reject: denied, dismissed, no device, device in useFour distinct denial paths, each needing its own message. Deny once, then re-open — most apps never recover.
③Hard-coded audio/webmSafari and iPad Safari do not produce webm. Test on real iPad — the school's actual device.
④Counter increments only on successFail the upload 5× — user gets unlimited attempts. Network throttle to trigger.
⑤catch sets error, offers nothingDead end for the learner. A classroom of 30 hitting this generates 30 support tickets.

#Test
①Two instances → real limit is 20/min, not 10. Verify against staging at production instance count.
②Expired, malformed, alg:none, valid token signed with the wrong key, token for a deleted user.
③Teacher token on a learner route → 403 not 500. Learner token on a teacher route → 403.

5.3 Service layer — where the rules are

src/services/attempt.service.ts
async function create(userId: string, exerciseId: string, clip: Clip) {
  const ex = await repo.findExercise(exerciseId);
  if (!ex) throw new NotFound();
  if (!await repo.userInClass(userId, ex.classId)) throw new Forbidden();  // ① ownership

  const used = await repo.countAttempts(userId, exerciseId);
  if (used >= ex.maxAttempts) throw new TooMany();                        // ② check…

  const score = scoreTranscript(clip.transcript, ex.referenceText);      // ③ our maths
  return repo.insertAttempt({ userId, exerciseId, score });                // ④ …then write
}
Check-then-act is a race

Steps ② and ④ are not atomic. Two concurrent submissions both read used = 2, both pass, both insert — a 4th attempt exists on a 3-attempt exercise. Only a unique constraint or a transaction with row locking fixes it. Test: fire two identical requests simultaneously and assert exactly one succeeds. Sequential testing can never find this.

③ costs money and can fail

Assert that a Speech failure does not consume an attempt, does not leave an orphan row, and does not lose the learner's clip.

06 Database testing · PostgreSQL4 p

6.1 Schema QA must know

CREATE TABLE users (
  id            uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  email         citext NOT NULL UNIQUE,        -- case-insensitive by type
  role          text NOT NULL CHECK (role IN ('learner','teacher','admin')),
  school_id     uuid NOT NULL REFERENCES schools(id),
  deleted_at    timestamptz                    -- soft delete: every query must filter
);

CREATE TABLE attempts (
  id            uuid PRIMARY KEY,
  user_id       uuid NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  exercise_id   uuid NOT NULL REFERENCES exercises(id),
  accuracy      numeric(5,2) CHECK (accuracy BETWEEN 0 AND 100),
  created_at    timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX idx_attempts_user_ex ON attempts(user_id, exercise_id);
ElementTest that proves it works
citext emailInsert A@school.edu, then a@school.edu — second must be rejected, else two accounts share a login
CHECK on roleDirect SQL insert of role='superadmin' must fail — proves the DB, not just the app, enforces it
ON DELETE CASCADEDelete a user, confirm attempts vanish. Then ask whether that is legal under the school's data-retention contract
deleted_atSoft-delete a learner, then run every list endpoint — one will still return them
Composite indexEXPLAIN the attempt-count query on staging; must be Index Scan, not Seq Scan
numeric(5,2)Score of 99.999 → rounds or errors? Confirm which, and that the UI agrees

6.2 SQL validation queries

-- Orphans: attempts whose exercise was hard-deleted
SELECT a.id FROM attempts a LEFT JOIN exercises e ON e.id = a.exercise_id
WHERE e.id IS NULL;

-- Soft-deleted users still reachable through a join
SELECT u.email FROM users u JOIN attempts a ON a.user_id = u.id
WHERE u.deleted_at IS NOT NULL;

-- Attempt-limit violations that the check-then-act race allowed through
SELECT user_id, exercise_id, count(*) FROM attempts
GROUP BY 1,2 HAVING count(*) > 3;

-- Cross-school leakage: a learner with attempts on another school's exercise
SELECT u.id FROM attempts a
  JOIN users u ON u.id = a.user_id
  JOIN exercises e ON e.id = a.exercise_id
WHERE u.school_id <> e.school_id;                -- must return zero rows, always

-- Is the query actually using the index?
EXPLAIN ANALYZE SELECT count(*) FROM attempts
WHERE user_id = $1 AND exercise_id = $2;
The cross-school query is the single most valuable check in this manual

Run it after any change to enrolment, class assignment, or reporting. A non-zero result means one school can see another school's learner data. That is a contract-terminating event, and it is invisible from the UI.

6.3 Migrations

Migration typeRiskQA action
Add nullable columnLowConfirm old API version still works — deploys are not atomic
Add NOT NULL columnHighRequires a default or a backfill; locks the table without one
Add indexMediumMust be CREATE INDEX CONCURRENTLY, or writes block during deploy
Rename columnHighBreaks the running old version mid-deploy. Expand/contract over two releases.
Drop columnHighIrreversible. Confirm no code path and no report reads it.
Change typeHighFull table rewrite plus lock. Test on a staging-sized copy and time it.
Rollback is a test case, not a hope

Every migration must be run down in staging before the release is approved. A migration without a tested rollback turns a 10-minute incident into a 4-hour one. Assert that data written after the up-migration survives the down-migration.
