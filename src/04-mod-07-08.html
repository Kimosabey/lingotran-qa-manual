7.2 Why this pipeline is unusually hard to test

PropertyConsequence for QA
Non-deterministicThe same clip can score 81 then 83. Assertions must use tolerance bands, never equality.
External and paidCI cannot call it on every run. Stub in CI; use a small real-audio suite nightly.
Device-dependentA laptop mic, an iPad mic, and a classroom headset produce materially different scores from the same speaker.
Accent-sensitiveThe failure mode is systematic, not random — see 7.3. This is the defect class most likely to reach production unnoticed.
Silently degradingIf the service returns a default or partial payload, the app shows a plausible score. Nothing looks broken.

7.3 The reference clip corpus

Maintain a fixed set of recordings in blob storage. Every release is scored against them and compared to the previous release. This is the only reliable regression signal for scoring quality.

ClipContentExpected bandCatches
REF-01Native speaker, clean audio, correct90–100Baseline drift
REF-02Learner, accented, correct words70–90Accent penalty — the critical one
REF-03Correct words, heavy classroom noise60–85Noise robustness
REF-04Wrong words, fluent delivery0–30Scoring fluency instead of accuracy
REF-05Half the sentence onlycompleteness < 60Completeness ignored
REF-06SilenceRejected before billingWasting paid API calls
REF-07A different language entirelyLow + no crashUnhandled service response
REF-0860 s at the duration limitScored, no timeoutGateway timeout on long clips
Known defect class · systematic false negatives

Lingotran's pronunciation feedback has historically penalised accented-but-correct speech, marking REF-02-type clips as errors. The learners most affected are exactly Lingotran's core users. This will never show up in a test suite that uses only native-speaker clips or stubbed responses — the stub always returns a good score. REF-02 must be in the nightly real-audio run, with a floor assertion, permanently.

Privacy — a standing check

Learner audio is personal data, and a large share of Lingotran's learners are minors. For any change touching capture or upload, confirm: audio goes only to the contracted Azure region, retention matches the school agreement, clips are deleted when a learner is removed, and no third-party endpoint appears in the network tab. Browser-native speech APIs in particular may transmit audio to servers outside the contracted sub-processor list — verify in DevTools, not in documentation.

7.5 Devices, browsers, and what they actually capture

Scores are compared across a class as though the audio were equivalent. It is not. The same learner reading the same sentence scores differently on three devices in the same room, and the device is invisible in the attempts table unless someone chose to record it.

Device in real classroomsWhat it actually producesFailure mode to force
Desktop Chrome, built-in micwebm/opus, 48 kHzBaseline. Also picks up the learner at the next desk — completeness scores inflate on a sentence that was never finished.
iPad Safari — the school's actual devicemp4/aac. Never webm.A hard-coded mimeType throws on construction, so recording never starts and the UI shows nothing (4.1 ③).
Bluetooth headsetDrops to ~8 kHz narrowband the moment the mic opensSame speaker, same words, scores collapse. See the box below.
USB classroom headset16 kHz mono — the best caseShared between classes and rarely checked. Test a physically damaged mic, not only a working one.

The Bluetooth downgrade

A Bluetooth headset plays audio at high quality, but the moment its microphone opens most stacks switch the link to a narrowband voice profile — roughly 8 kHz mono. Pronunciation assessment on 8 kHz audio has lost most of the consonant detail it scores against, so the learner is marked down for their headset rather than their speech. It reproduces on any pairing, looks exactly like a learner getting worse, and is invisible in the attempts table. Record input device and sample rate alongside every attempt — without them this defect is unfalsifiable.

7.6 Quota and throttling

The institution multiplier lands harder here than anywhere else in the stack. Thirty learners press submit inside the same minute, and every one of those becomes a paid, rate-limited call to an external service.

LimitWhere it bites firstTest
Concurrent requests per resourceOne class submitting together — not total daily volumeFire 30 assessments simultaneously against staging; assert no 5xx reaches a learner
Transactions per secondTimetable peak, several classes at onceOverlap two class-burst scenarios (9.1)
Monthly quotaLate in the billing period, silentlyConfirm the alert fires approaching the cap, not on hitting it
Per-request durationREF-08, at the 60 s boundaryAssert the gateway timeout exceeds the longest permitted clip
test/speech/quota.spec.ts
// 30 learners, one classroom, one minute — the shape that actually breaks it
test('a full class submitting together degrades, never errors', async () => {
  const results = await Promise.all(
    Array.from({ length: 30 }, () => assess(REF_01, referenceText))
  );

  // Throttling is acceptable. A raw failure reaching the learner is not.
  for (const r of results) {
    expect(r.status).not.toBe(500);
    if (r.status === 429) expect(r.headers['retry-after']).toBeDefined();
  }

  // And a throttled call must never consume one of the learner's three attempts
  expect(await countAttempts(uid, eid)).toBe(results.filter(r => r.ok).length);
});
Retries amplify the burst

A client that retries on 429 without backoff turns thirty requests into ninety against a service already refusing them, and the class never recovers inside the lesson period. Assert that retry is capped and jittered, and that a throttled attempt is not counted against the learner.

7.7 The phoneme feedback panel

The overall score is one number and easy to check. The panel beneath it renders one marker per phoneme, and is where payload and UI most often disagree.

CaseExpectedWhy it breaks
Payload omits phonemesOverall score shown, panel hiddenPartial responses are normal under load, and a missing array reads as undefined.map
Phoneme count ≠ words spokenPanel aligns to what was assessed, not the reference textPartial speech (REF-05) returns fewer phonemes than the sentence contains
Score exactly on a colour thresholdOne documented bucket, deterministic60.0 rendering as "needs work" in one view and "good" in another
Non-Latin reference textRenders and aligns correctlyDevanagari and Tamil clusters span several code units; naive per-character mapping misaligns every marker (3.4)
Long sentence at the 60 s limitWraps or scrolls inside the panelFixed-width rows clip silently on iPad portrait — the school's device again
Second attempt after a firstPanel resets completelyStale markers from the previous attempt persist beneath the new score
Colour alone is not feedback

Phoneme quality is almost always rendered red / amber / green. To a colour-blind learner that panel carries no information, and a screen reader announces a row of meaningless spans. Every marker needs a text or shape equivalent and an accessible name. This is the accessibility defect most likely to survive an axe scan, because the contrast passes and the markup is technically valid (9.3).

08 Automation · ATDD to pipeline5 p

8.1 TDD and ATDD — who owns what

Test-Driven Development is a developer practice. QA never runs the red-green-refactor loop. What QA needs is literacy: the ability to read a test-driven pull request and judge it.

Read the PR and askWhat a bad answer looks like
Do the tests assert behaviour or implementation?Assertions on mock call counts and internal state — they will pass through a refactor that breaks the feature
Were they written with the code or after?One giant test per function, named test1, added in the final commit
What is already covered at unit level?Nothing — so your E2E suite must carry the whole burden
What can unit tests structurally not reach?Speech responses, migration order, real microphones, multi-instance behaviour

ATDD is the QA-owned equivalent. Acceptance criteria are written as Given/When/Then before the sprint opens (Module 3.2), agreed with the developer, and become the Playwright spec. Same tests-first discipline, at the layer where QA has authority.

The test to apply

Automate when frequency × consequence > cost of maintenance. Most flaky suites exist because someone automated something that runs twice a year.

8.3 Playwright patterns

e2e/attempts.spec.ts
test('learner cannot exceed the attempt limit', async ({ page, request }) => {
  // Set up state through the API, never through the UI — 10× faster, no flake
  const { token } = await seedLearner(request, { school: 'school.edu' });
  await loginWithToken(page, token);

  await page.goto('/lessons/greetings/ex/1');
  for (let i = 0; i < 3; i++) await submitClip(page, 'REF-01.webm');

  // Assert on a role and accessible name, not a CSS class
  await expect(page.getByRole('button', { name: 'Record' })).toBeDisabled();
  await expect(page.getByText('No attempts remaining')).toBeVisible();

  // Then verify at the source of truth — the UI can lie
  const rows = await db.query(
    'SELECT count(*) FROM attempts WHERE user_id=$1 AND exercise_id=$2', [uid, eid]);
  expect(rows[0].count).toBe('3');   // pg returns bigint as string
});
RuleWhy
Seed via API, assert via UIUI setup is the single largest source of flake and runtime
Locate by role and accessible nameSurvives restyling, and doubles as an accessibility check
Never waitForTimeoutA fixed sleep is either flaky or slow, usually both
One assertion theme per testA failure should name the defect without a debugger
Verify at the databaseA green UI over a wrong row is the defect that reaches production
Fresh data per testShared fixtures create order dependence, which surfaces only in CI
Flake policy

A spec that fails intermittently is worse than no spec — it trains the team to re-run the pipeline. Quarantine on the second unexplained failure, fix within one sprint, delete if unfixed. Track flaky rate as a first-class metric.
