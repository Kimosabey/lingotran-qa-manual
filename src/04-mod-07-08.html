07 The speech pipeline6 p

The heart of the product, and the part where "the tests pass" and "the product works" most often disagree.

What we actually run today

Lingotran uses the browser Web Speech API — Google-backed ASR and STT in Chrome, plus speechSynthesis for TTS. We do not use a paid pronunciation-assessment service. That single fact drives everything below, and most of it is uncomfortable.

7.1 The path

Mic ──▶ getUserMedia ──▶ Web Speech API (runs in the browser)
                               │
                               │  audio leaves the device to Google's servers
                               ▼
                    transcript + confidence
                               │
                    POST /attempts { transcript, referenceText }
                               ▼
              Service compares transcript to reference text
              (text similarity — this is where the "score" is invented)
                               ▼
              attempts table ──▶ progress report ──▶ teacher dashboard

TTS: speechSynthesis ──▶ voice from the device, not from us

7.2 What this means for testing

A speech-scoring service would hand us accuracy, fluency and per-phoneme numbers. The Web Speech API hands us a line of text. Everything else we build ourselves, so every scoring bug is ours.

PropertyWhat it means for QA
No real scoringThere is no accuracy or phoneme score to trust. The score is our own text comparison, so test our maths, not a vendor's.
Not on every browserSpeechRecognition is a Chrome and Edge feature. iPad Safari is unreliable or missing. See the box below — this is the biggest risk in the manual.
Audio leaves the deviceThe browser sends learner speech to Google to transcribe. Learners are children. This is a data-protection question, not a technical one (7.4).
Needs the networkNo connection, no transcript. School wifi drops mid-lesson all the time.
Not deterministicThe same speech can transcribe two ways. Never assert an exact string.
No contract, no quota pageIt is a free browser feature. Limits are undocumented and can change without warning.
Fails quietlyAn empty or partial transcript still produces a number. The learner sees a plausible score that means nothing.
The iPad problem — read this first

Schools run iPads, and browser speech recognition is a Chrome feature — on iPad Safari it is missing or unreliable. The main thing Lingotran does may not work on the main device our customers own. Test this before anything else, on a real iPad, on school wifi. If it fails, that is a product decision, not a bug: say so early rather than filing it and waiting.

7.3 The reference clip corpus

A fixed set of recordings we replay every release and compare against the last run. Because we invent the score ourselves, this is the only way to notice it changing.

ClipWhat is on itWhat we expectWhat it catches
REF-01Native speaker, clean audio, correct wordsTranscript matches; score highBaseline drift
REF-02Learner, strong accent, correct wordsTranscript still matchesAccent failure — the critical one
REF-03Correct words, noisy classroomTranscript mostly matchesNoise handling
REF-04Wrong words, said fluentlyLow scoreRewarding confidence over correctness
REF-05Half the sentence onlyLow completenessPartial speech scored as complete
REF-06SilenceRejected, no attempt usedEmpty transcript scored as a fail
REF-07A different languageLow score, no crashUnhandled empty result
REF-0860 s, at the length limitHandled, no cut-offRecognition stopping early on long speech
REF-02 · the defect that matters most

Our learners have accents. Speech recognition is weakest on accented speech. So the recogniser mishears a learner who said the words correctly, our comparison sees a mismatch, and the learner is marked wrong.

Read that again: the learner is punished for the recogniser's mistake, not their own. It looks exactly like a learner who is getting worse. It will never appear in a test suite built on clean native-speaker audio or a stub, because both always return the right words. REF-02 belongs in the nightly run permanently, with a floor assertion.

Privacy — the standing check, and it is now the main one

The browser sends learner speech to Google to be transcribed. Many Lingotran learners are children. Before any change touching capture, confirm all of these: the school agreement actually permits it, Google is named as a sub-processor, parents and schools have been told, and nothing is retained that we have not disclosed.

This used to be a footnote about browser APIs. With the Web Speech API it is the architecture. Check it in DevTools and in the signed agreement — not in documentation. If the two disagree, stop and escalate; do not open a ticket and continue.

7.5 Devices, browsers, and what they actually capture

Scores are compared across a class as though the audio were equivalent. It is not. The same learner reading the same sentence scores differently on three devices in the same room, and the device is invisible in the attempts table unless someone chose to record it.

Device in real classroomsWhat it actually producesFailure mode to force

iPad Safari — the school's actual devicemp4/aac. Never webm.A hard-coded mimeType throws on construction, so recording never starts and the UI shows nothing (4.1 ③).

The Bluetooth downgrade

The moment a Bluetooth microphone opens, most stacks drop the link to a narrowband voice profile — roughly 8 kHz mono. That strips the consonant detail recognition depends on, so the learner is marked down for their headset rather than their speech. It reproduces on any pairing and looks exactly like a learner getting worse. Record input device and sample rate on every attempt — without them this defect is unfalsifiable.

7.6 Limits we do not control

There is no bill and no quota page, so it is tempting to assume there is no limit. There is — we just cannot see it. Thirty learners in one room speak at the same time, through one school connection.

LimitWhere it shows up firstHow to test it
Undocumented throttlingA whole class speaking at once from one networkRun 30 real browsers on one connection. A lab of one laptop proves nothing
Recognition stops on silenceA learner who pauses to think mid-sentencePause 3–5 s mid-sentence and check what is kept
Speech length capLong sentences, REF-08Read for the full 60 s and check nothing is cut
Behaviour changes without noticeAny day, with no release of oursThe nightly REF run is the only warning we get
Nobody owes us an SLA

This is a free browser feature, not a contracted service. It can change or throttle with no notice and no support ticket to raise. That is a real product risk and it belongs in the release conversation, not just in a test plan. The nightly REF corpus is our only early warning — if it is not running, we find out from a school.

7.7 The feedback panel

We have no phoneme data, so the panel can only show what we do have: which words the recogniser heard and which it did not. Being honest about that is the whole design problem.

CaseWhat should happenWhy it breaks
Transcript comes back emptyAsk them to try again — do not show 0%An empty string compares as "everything wrong"
Recogniser heard a similar wordTreat near-matches kindly, or say we are unsure"ship" for "sheep" is a recogniser limit, not a learner error
Learner said more than askedScore the required words onlyExtra words drag a text-similarity score down unfairly
Word counts do not line upAlign to what was heard, not to the referencePartial speech (REF-05) returns fewer words than the sentence has
Score sits exactly on a thresholdOne documented bucket everywhereThe same 60% shown as "needs work" in one view and "good" in another
Non-Latin reference textWords split and align correctlySplitting on spaces or characters breaks scripts that do not work that way (3.4)
Second attemptPanel clears completelyOld words linger under the new score
Colour alone is not feedback

Right and wrong words are almost always red and green. A colour-blind learner gets nothing from that, and a screen reader reads a row of meaningless words. Every marker needs text or shape as well as colour. This is the a11y defect most likely to pass an axe scan — the contrast is fine and the markup is valid (9.3).

Say "we could not hear you", not "you were wrong"

Because the transcript is the only evidence we have, we genuinely cannot tell a mispronounced word from a misheard one. The wording of the feedback has to respect that. A child told they are wrong when they were right stops trusting the product, and a class of thirty stops together. Test the wording, not only the number.

08 Automation · ATDD to pipeline5 p

8.1 TDD and ATDD — who owns what

Test-Driven Development is a developer practice. QA never runs the red-green-refactor loop. What QA needs is literacy: the ability to read a test-driven pull request and judge it.

Read the PR and askWhat a bad answer looks like
Do the tests assert behaviour or implementation?Assertions on mock call counts and internal state — they will pass through a refactor that breaks the feature
Were they written with the code or after?One giant test per function, named test1, added in the final commit
What is already covered at unit level?Nothing — so your E2E suite must carry the whole burden
What can unit tests structurally not reach?Speech responses, migration order, real microphones, multi-instance behaviour

ATDD is the QA-owned equivalent. Acceptance criteria are written as Given/When/Then before the sprint opens (Module 3.2), agreed with the developer, and become the Playwright spec. Same tests-first discipline, at the layer where QA has authority.

The test to apply

Automate when frequency × consequence > cost of maintenance. Most flaky suites exist because someone automated something that runs twice a year.

8.3 Playwright patterns

e2e/attempts.spec.ts
test('learner cannot exceed the attempt limit', async ({ page, request }) => {
  // Set up state through the API, never through the UI — 10× faster, no flake
  const { token } = await seedLearner(request, { school: 'school.edu' });
  await loginWithToken(page, token);

  await page.goto('/lessons/greetings/ex/1');
  for (let i = 0; i < 3; i++) await submitClip(page, 'REF-01.webm');

  // Assert on a role and accessible name, not a CSS class
  await expect(page.getByRole('button', { name: 'Record' })).toBeDisabled();
  await expect(page.getByText('No attempts remaining')).toBeVisible();

  // Then verify at the source of truth — the UI can lie
  const rows = await db.query(
    'SELECT count(*) FROM attempts WHERE user_id=$1 AND exercise_id=$2', [uid, eid]);
  expect(rows[0].count).toBe('3');   // pg returns bigint as string
});
RuleWhy
Seed via API, assert via UIUI setup is the single largest source of flake and runtime
Locate by role and accessible nameSurvives restyling, and doubles as an accessibility check
Never waitForTimeoutA fixed sleep is either flaky or slow, usually both
One assertion theme per testA failure should name the defect without a debugger
Verify at the databaseA green UI over a wrong row is the defect that reaches production
Fresh data per testShared fixtures create order dependence, which surfaces only in CI
Flake policy

A spec that fails intermittently is worse than no spec — it trains the team to re-run the pipeline. Quarantine on the second unexplained failure, fix within one sprint, delete if unfixed. Track flaky rate as a first-class metric.
